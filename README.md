# AgentTrust MVP（第一版）

面向智能体互联网的可信服务发现与抗欺骗协同调度系统 —— 可运行原型。

核心思路：让多个模拟智能体登记自己的能力，系统根据**能力匹配度**、**基于历史实际结果计算的可信度**、
**响应延迟**三方面综合排序。重点验证系统**不会盲信智能体的自我宣称成功率**。

## Windows PowerShell 启动

建议 Python 3.11 或 3.12。**以下命令全部在项目根目录 `agenttrust\` 下执行。**

```powershell
py -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python -m uvicorn app.main:app --reload
```

如果虚拟环境激活被系统策略阻止（不想激活也能用，直接指定解释器路径）：
```powershell
py -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload
```

> ⚠️ 启动命令是 `app.main:app` 而不是 `main:app`。
> 因为入口文件在 `app/` 子目录里，`app.main` 表示"app 目录下的 main 模块"，最后的 `:app` 是模块里的 FastAPI 变量名。

浏览器打开 http://127.0.0.1:8000/docs （FastAPI 自动生成的交互式接口文档）。

## 运行对照实验（核心交付物）

```powershell
.\.venv\Scripts\python.exe run_experiment.py
```

默认跑 `5 次独立试验 × 100 轮 × 3 种策略 = 1500 次调度决策`，几秒完成。

自定义规模与复现：
```powershell
# 快速跑一次看看
.\.venv\Scripts\python.exe run_experiment.py --trials 1 --rounds 50

# 加大规模，结论更稳
.\.venv\Scripts\python.exe run_experiment.py --trials 10 --rounds 500 --seed 7
```

结果保存在 `results/` 目录：

| 文件 | 内容 | 用途 |
|---|---|---|
| `*_rounds.csv` | 逐轮原始记录（每行一次决策） | **参赛要求的原始实验数据** |
| `*_summary.csv` | 每个策略一行的汇总指标 | 直接导入 Excel 画对比图 |
| `*_meta.json` | 实验参数、智能体设定、已知局限 | 证明实验可复现、可追溯 |

## 实验结论（真实运行结果，非预设）

参数：5 次独立试验 × 100 轮 × 3 种策略，随机种子 42，任务需求能力 `research`。

| 策略 | 任务成功率 | 欺骗智能体被选中率 | 前 20 轮被骗率 | 20 轮后被骗率 | 平均延迟 |
|---|---|---|---|---|---|
| 仅能力匹配 | **16.20%** | 100.00% | 100.00% | 100.00% | 150.0ms |
| 随机选择 | 58.40% | 29.20% | 29.00% | 29.25% | 259.8ms |
| **可信度感知** | **78.40%** | **1.20%** | 6.00% | **0.00%** | 324.4ms |

**三个关键发现（均可在 `results/` 里核对原始数据）：**

1. **"仅能力匹配"比随机乱选还差得多（16.20% vs 58.40%）。**
   原因：任务只要求 `research`，三个智能体能力完全匹配，能力项恒定 1.0 失去区分作用，
   于是退化为"只看延迟"，而虚报型智能体延迟最低（150ms），
   结果它 500 轮里被选中 500 次 —— 一个看起来更"聪明"的策略反而被骗子完全占据。

2. **可信度感知调度把欺骗被选中率从 29.20% 压到 1.20%，任务成功率提升 20 个百分点。**
   20 轮之后欺骗被选中率降为 **0.00%**，说明系统确实学会了识别虚报型智能体。

3. **冷启动阶段所有策略都会先被骗（前 20 轮被骗率 6.00%）。**
   第 1 轮三个智能体可信度都是先验值 0.5，并列时只能靠延迟决胜，
   而虚报型延迟最低 —— 所以**第 1 轮必然选中骗子**。算法需要真实战绩才能起作用。

## 已知局限（必须如实说明）

以上结论的适用范围有明确边界，报告和答辩中不能省略：

1. **智能体参数是人为设定的演示值**，不是真实系统测量数据。成功率 0.82 / 0.75 / 0.15、
   延迟 430 / 180 / 150ms 都是为了构造"虚报型看起来最有吸引力"的场景而设计的。

2. **本实验无法体现"能力匹配"项的作用。** 任务只要求 `research` 一项，
   三个智能体都具备，能力匹配度恒为 1.0。要验证能力项，需要设计多能力、多任务类型的实验。

3. **算法存在严重的"过早锁定"问题（已实测确认）。** 追踪发现：
   第 1 轮必然选中 Claimed-Expert 并失败，第 2 轮选中 Fast-Generalist。
   若 Fast 成功，它此后 100 轮里被选 99 次；若 Fast 失败，则 Reliable 被选 98 次。
   **即一次随机成败就锁定了后续全部选择**，说明算法用极少证据就过度承诺，
   缺乏探索机制（不会去验证"另一个智能体是不是更好"）。
   5 次试验中 4 次锁定 Reliable、1 次锁定 Fast，差异完全来自这一次抛硬币。

4. **延迟的作用被严重削弱。** 受上一条影响，算法几乎总是重复选择同一个智能体，
   导致"延迟"这一维度在实际决策中影响很小（可用实验参数改动权重后重跑验证）。

5. **可信度公式为拉普拉斯平滑**，属于基础做法，尚未与贝叶斯估计、
   时间衰减、异常检测等更复杂方法做对照实验。

## 演示顺序
1. `POST /demo/reset` 加载三个模拟智能体。
2. `GET /agents` 查看历史可信度。
3. `POST /discover` 请求体：
```json
{"task_id":"task-001","required_capabilities":["research","summarization"]}
```
4. 从 `/agents` 复制虚报型智能体的 `agent_id`，向 `POST /results` 发送：
```json
{"agent_id":"替换为实际ID","success":false,"latency_ms":500}
```
5. 再次查看 `/agents` 和 `/discover`，观察分数变化。

## 演示智能体

| 名称 | 宣称成功率 | 实际战绩 | 可信度 | 说明 |
|---|---|---|---|---|
| Reliable-Researcher | 0.82 | 8 胜 2 负 | 0.714 | 可靠型 |
| Fast-Generalist | 0.75 | 5 胜 3 负 | 0.583 | 快速通用型 |
| Claimed-Expert | **0.99** | **1 胜 7 负** | **0.250** | 虚报型（抗欺骗验证对象） |

可信度公式：`(成功次数 + 2) / (成功次数 + 失败次数 + 4)`，即拉普拉斯平滑。
**`claimed_success_rate` 被存储但从不参与打分** —— 这是刻意的设计，用于验证抗欺骗能力。

## API
- `GET /` 健康检查
- `POST /agents` 注册智能体
- `GET /agents` 查询智能体
- `POST /discover` 能力匹配与可信度排序
- `POST /results` 记录实际结果并更新可信度
- `POST /demo/reset` 重置演示数据
- `GET /history` 查询记录

> **注意区分两套数据**：
> - `/demo/reset` 的演示战绩是**硬编码**的（如"8 胜 2 负"直接写入），只用于**接口演示**。
> - `run_experiment.py` 的实验数据是**真实模拟跑出来的**，由概率产生，才可作为参赛证据。
>
> 这两者不要混用，更不要把演示数据当成实验结果。

## 其他限制

- **内存存储**：数据存在 Python 字典里，重启服务就清空。尚未接入 SQLite。
- **`/discover` 不返回"最终选中了谁"**，因此接口本身无法统计欺骗智能体被选中比例。
  实验框架（`app/experiment.py`）已经补上了这个指标，但 API 尚未暴露。
